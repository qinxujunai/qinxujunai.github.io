# 工程做法：从 mattpocock/skills 借鉴什么（2026-11-08）

来源：github.com/mattpocock/skills（Matt Pocock 的 Claude Code / Codex 技能集，副标题「给真正的工程师，不是 vibe coding」）。读的是 README 和 engineering、productivity 两组技能的 SKILL.md。下面只记对这几个仓库有用的，和我们已经在做的对照。

## 它的核心主张（四个失败模式，四个解法）
1. **做出来的不是想要的** → 动手前先「拷问」（grill-me）：AI 一条条问，直到每个分支都定下来。
2. **AI 说话啰嗦、名字乱起** → 一份共享词表 `GLOSSARY.md`，外加每个难解释的决定写一份短 ADR（`docs/adr/0001-xxx.md`）。
3. **代码跑不通** → 反馈回路：类型、浏览器、自动化测试；测试先红后绿（TDD），只在约定好的「接缝」（公开接口）上测，不测内部实现。修 bug 先造一个「对这个 bug 会变红」的最小回路。
4. **越改越乱** → 深模块（Ousterhout）：小接口、藏住大量逻辑；删除测试：删掉一个模块，复杂度是消失（它是空壳）还是散到各处（它有价值）。

## 我们已经做到的
- 反馈回路：`npm run check`、`qa`、`test-player`、`test-signal-card`，`ship` 每次全跑，失败不推送。
- 先红后绿：卡片测试换回旧代码会失败（2026-11-08）。
- 独立审查：大改交给没参与修改的智能体（相当于它的 code-review 分两路：守规矩 + 符合需求）。
- 接口稳定：`build.mjs` 的 `--profile` 是一个小接口，求职站全靠它。

## 值得借鉴、我们还没做的（按收益排）
1. **常驻文件太大。** `AGENTS.md`（约 38KB）和 `CLAUDE.md`（约 29KB）每次会话都整份读进上下文，约 2 万多 token：既耗额度，也让真正的禁令被稀释。它的原则：常驻文件只放「去哪找什么」的指针和少数红线；逐版记录、决策原因放 `docs/`，按需读。**建议**：把两份收到各 5KB 以内，其余移到 `docs/decisions.md`（决策记录）和 `docs/standards.md`（写法、样式、交互数值），内容一字不丢。要他同意再动。
2. **规矩分两类。** 机械的（标点、禁词、体积、隐私名单）交给 `check.mjs` 自动拦——我们已经在做，继续把能机器检查的从文字规矩里搬出去；需要判断的（口吻、不说教）留给审查智能体，不放常驻文件。
3. **决策用短 ADR。** 每个「为什么这样、否掉了什么」一份几行的文件，比在长日志里翻好找，也不会被下一位智能体推翻。
4. **PR / 提交说明的形状**：一句话改了什么 + 改前改后的证据（截图或测试输出）+ 这次能不能撤回（单向门 / 双向门）、影响多大。
5. **会话结束做复盘（retro）**：这次哪里绕了远路、哪条规矩没起作用、哪个检查本可以自动拦住，改环境而不是只改这一次的代码。

## 对去大厂的意义
大厂代码评审看的就是这几样：改动小而可撤回、有测试证明、命名统一、模块边界清楚、说明里有证据。面试被问「你怎么保证 AI 写的代码可靠」，可以直接讲：先拷问需求、在接口上写先红后绿的测试、每次上线自动跑检查、独立智能体审查、失败不发布——并拿这几个仓库作证据。
