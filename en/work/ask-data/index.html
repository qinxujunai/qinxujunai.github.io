The problem

When a company asks its data a question, the hard part isn’t getting a model to write SQL; it’s getting people to trust the numbers. Models invent a plausible figure, a column that doesn’t exist, or their own idea of which countries count as “developed”.

Ask Data takes away everything a model could invent: it only turns the question into a query and writes a sentence; the numbers can only come from the database.

Hard parts

  • Models invent numbers. Even with the right query, the answer may contain a figure it worked out or misremembered.
  • Definitions drift. “Latest”, “world average”, “developed countries” mean different things to different people, and to models.
  • A model-written query might change data, run for ages, or simply be wrong the first time.
  • Visitors without a model key should still be able to use it.

Scope

Does

  • Questions over 17 World Bank indicators, 1990–2024
  • Trends, rankings, comparisons, shares, first-time crossings
  • The query, the steps and the source with every answer

Does not

  • Questions that need other data or outside knowledge
  • Holding visitors’ model keys
  • Accuracy claims (no evaluation yet)

How it’s built

  1. 1Retrieve

    • Indicator notes, business terms, verified examples
    • Countries in the question, resolved to codes
    • BM25, with Chinese indexed as character pairs

  2. 2Write the query

    • A verified question uses its verified query
    • Otherwise DeepSeek sees only what was retrieved plus the schema, and writes one SQL query

  3. 3Check

    • One read-only statement, at most 500 rows
    • If it fails, the reason goes back to the model for one repair

  4. 4Run

    • SQLite in a Web Worker in the browser
    • The connection itself is read-only; anything past 4 s is stopped

  5. 5Answer

    • The model writes the sentence; numbers are placeholders pointing at result cells
    • Code fills them in by unit; a number the model typed itself hides the sentence

The same idea as AI Signal: the model cites IDs, and code fills in the links and numbers.

Trade-offs

  • The database lives in the browser

    WhyIt is 1.5 MB; no server, and the data never leaves the visitor’s machine

    Given upA backend

  • Keyword retrieval, no vector store

    WhyA few dozen definitions and examples: keywords are enough, and explainable

    Given upA vector database from day one

  • Visitors bring their own key; the browser calls DeepSeek directly

    WhyFully static, and nobody else’s key to hold

    Given upA proxy server

  • Verified questions skip the model

    WhyWorks without a key, and a verified answer beats a fresh one

    Given upSending every question to the model

Evidence

  • Seven groups of automated tests: all 21 verified questions run for real; write statements are blocked and the connection itself refuses writes; a simulated model writes a bad query, gets blocked, repairs it and answers.
  • Three paths tried in a browser (a verified question, a free question without a key, a free question with one) on phone and desktop, light and dark: no errors, zero accessibility violations.
  • On the live site, a verified question answers in about two seconds.

Timeline

Still missing

  • No accuracy evaluation yet. The script exists: ask the model every verified question with its own example held out, compare the results, with and without retrieval. It needs a key to run.
  • Retrieval is keyword-based; past a few hundred definitions and examples it should become vector or hybrid search.
  • One dataset only, and it doesn’t update itself.
